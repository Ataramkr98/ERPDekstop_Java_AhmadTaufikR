# Architecture and implementation conventions

The existing three modules remain the deployment boundary. `erp-core` owns the JPA entities, the shared REST/persistence engine, business services, security and Flyway migrations. `erp-backend` supplies a standalone host. `erp-desktop` starts JavaFX immediately and brings up Quarkus on a background thread; its REST client connects only to loopback.

## Record contract

All business entities extend `BaseEntity`. Audit fields, company ownership, active state and optimistic-lock version are shared. Fields use Java types (`BigDecimal` for amounts, `LocalDate` for business dates, `Instant` for timestamps) and explicit JPA columns. Panache may enhance public fields to protected fields; shared reflection handles both and excludes static, synthetic, JPA-transient and secret fields.

Resources extend `CrudResource` and declare their concrete entity type and search fields. The shared surface supplies search, field filters, sorting, pages, CRUD, metadata and CSV import/export. `RecordPolicy` guards administrative access, company ownership, generated records and posted documents. `EntityValidation` checks column requirements and sizes before writes. `ReferenceValidation` resolves known ID references from the module registry and guards posted parent documents when editing lines. Unknown domain-specific ID names require an explicit mapping when adding new modules.

Update requests must carry the version read with the record. Server code checks that version and Hibernate checks again when committing. Creation fields are server-owned. Sensitive user fields are excluded from metadata, export and snapshots; password input is write-only and hashed on the server. Basic authentication is disabled. The signing keypair is generated per local profile by the launcher.

Audit entries commit in the same transaction as a business write. Audit, stock balances, movements, matching output and journal entries/lines cannot be edited through generic CRUD. Business services lock records and check their company before posting. Company locking serializes financial updates in this desktop-oriented implementation; higher throughput would call for a more granular locking strategy.

## JavaFX

`Catalog` derives from the core `ModuleRegistry`, avoiding a separate generated endpoint list. `MainWindow` disposes the previous page before navigation or sign-out. The overview reads company counts and recent activity from `/api/overview`. It never substitutes sample metrics for database results.

`EntityView` stores JSON records directly as table rows, so selection remains attached to the correct ID after sorting. Sorts and enum filters are sent to the server. `RecordDialog` uses metadata to build typed, scrollable forms and preserves the concurrency version. `Ui` owns the background executor and shared presentation helpers. Network requests and file import/export run off the JavaFX thread; their inputs are captured before dispatch. Disposal prevents late callbacks from replacing another screen's status. The stylesheet in `styles/app.css` centralizes colors, spacing and typography.

## Database and packaging

Migrations are in `erp-core/src/main/resources/db/migration`. Never rewrite an applied migration, baseline an unknown existing schema automatically, or clean a production database. The application runs pending Flyway migrations on startup. `RuntimeConfigSource` converts PostgreSQL `DATABASE_URL` credentials and query options to the JDBC properties; passwords are never included in JDBC URLs generated by the adapter.

Windows stores the supplied URI through DPAPI-protected `PSCredential` XML in the user's local profile. The launcher decrypts it only into the child process environment. It supplies per-profile signing key paths, and skips local PostgreSQL. Build tasks run before credential loading and temporarily clear connection secrets inherited from the environment. The source distribution excludes credentials, private keys, logs and build artifacts.

## Adding a feature

Add domain behavior to a transactional service and expose explicit action endpoints, keeping validation and invariants out of JavaFX. Add any record to `ModuleRegistry`; use consistent metadata types and protected server-owned fields. Add a focused regression test for the invariant and, for database behavior, an isolated backend integration test. Keep advertised functionality aligned with implemented behavior; record-definition modules must not imply that unimplemented automation engines are running.
